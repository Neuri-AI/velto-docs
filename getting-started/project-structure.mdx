You've already built a native window, created your first reusable component, and made a button respond to clicks. So far, you've worked mainly in `main.py`.

As your application grows, you'll want a place for new components, screens, images, and configuration. **Velto CLI creates those folders for you** when you initialize a project.

In this lesson, you'll explore the generated structure and learn where to put things. You don't need to reorganize your application yet.

## 1. Generate a project

If you've followed [Getting Started](/getting-started/overview), you already have a Velto project. You can continue using it.

To see a fresh project structure, create another application with Velto CLI:

```bash
velto init --name demo --framework pyside6
```

Open its directory:

```bash
cd demo
```

We'll use `demo` as the project name in the examples below. Your folder will have a different name if you chose one.

│   │   └── icons/

│   │       ├── 128.png

This might look like a lot of files for a small application. You won't need to edit most of them to keep learning Velto.

Let's focus on the folders you'll use most often.

## 3. Where does your Python code go?

### `main.py` — Your application entry point

`main.py` is where your application starts. You've already used it in [Hello World](/getting-started/hello-world), [Your first component](/getting-started/first-component), and [Your first interaction](/getting-started/first-interaction).

For a small learning project, it's perfectly fine to keep your components in this file.

As your application grows, however, putting every component and screen in `main.py` can make it difficult to navigate. That's why the generated project includes `components/` and `views/`.

You don't need to learn the application lifecycle again here; the important point is that **`main.py` remains the entry point even when you move interface code into other files**.

### `components/` — Reusable interface pieces

Use `components/` for UI elements you want to reuse in different parts of your application.

For example, the `Welcome` and `Counter` components you created in previous lessons could eventually live here:

```text
components/
├── welcome.py
└── counter.py
```

A component file might contain:

```python
# components/welcome.py
from velto.ui import component, psx


@component
def Welcome(name: str):
    return psx("""
        <Text>Welcome, {name}!</Text>
    """)
```

Then import it from `main.py`:

```python
from components.welcome import Welcome
```

The component works the same way as before. You've simply moved its definition to a separate file.

<Note>
  The generated `components/` folder initially contains only `.gitkeep`. You create your own Python files when you need them.
</Note>

### `views/` — Larger sections of your interface

Use `views/` to organize larger sections of an application, such as a dashboard, a settings screen, or a profile page.

For example, an application might eventually contain:

```text
views/
├── dashboard.py
└── settings.py
```

A **view** is a useful way to organize a larger piece of interface. It doesn't require a different programming language or a separate UI framework: you can build views with the same PSX Markup and components you've already learned.

The distinction is mainly about responsibility:

| `components/` | `views/` |
| --- | --- |
| Small or reusable interface pieces | Larger sections or screens |
| Examples: greeting, counter, toolbar | Examples: dashboard, profile, settings |
| Often used inside multiple views | Often assembled from several components |

This is a suggested organization, not a rule that every small application must follow.

## 4. Where do images and icons go?

The `resources/` directory holds assets used by your application.

Your generated project already includes icon files:

- **`resources/base/icons/`** contains shared icons and `.ico` files.
- **`resources/linux/icons/`** contains Linux icon sizes.
- **`resources/mac/icons/`** contains macOS icon sizes.

These are part of the generated project's resources, including assets that may be used for platform-specific application packaging.

You can also organize additional images and other application assets under `resources/` as your project grows.

For now, you don't need to modify the generated icons to continue learning how to build interfaces.

## 5. What are the JSON files in `settings/`?

The `settings/` folder contains the configuration files generated for your application:

```text
settings/
├── base.json
├── linux.json
├── mac.json
├── release.json
├── secrets.json
├── sign.json
└── windows.json
```

They separate application configuration from your PSX Markup.

At a high level:

| File | Purpose |
| --- | --- |
| `base.json` | Shared application configuration |
| `linux.json` | Linux-specific configuration |
| `mac.json` | macOS-specific configuration |
| `windows.json` | Windows-specific configuration |
| `release.json` | Release-related configuration |
| `secrets.json` | Configuration for sensitive values |
| `sign.json` | Application signing configuration |

Treat real secrets and signing credentials as sensitive; consult the configuration guide for supported handling. You don't need to memorize the available settings now. The important idea is that **window and application configuration belongs in settings, not in a `<Window>` tag inside your markup**.

For the supported fields, platform behavior, and examples, see [Configuration files](/configuration/configuration-files).

## 6. What about the other files?

The remaining files support the project itself:

| File | What it's for |
| --- | --- |
| `pyproject.toml` | Python project metadata and dependency configuration |
| `poetry.lock` | Records resolved dependency versions for reproducible installation |
| `README.md` | Information and instructions about your project |
| `LICENSE` | The project's license text |
| `.gitignore` | Tells Git which generated or local files to ignore |
| `.gitkeep` | Keeps otherwise-empty directories in version control |

You may edit `README.md` as you document your project, and `pyproject.toml` as you manage dependencies. You don't need to change these files just to add another PSX component.

## 7. Organize the app you've been building

Let's connect this structure to what you've already learned.

Right now, your `main.py` contains `Welcome`, `Counter`, and your application class. That is a good starting point.

When you want to split the code into files, you could organize it like this:

```text
demo/
├── components/
│   ├── welcome.py
│   └── counter.py
├── views/
│   └── .gitkeep
├── resources/
├── settings/
└── main.py
```

The shortened tree above highlights only the relevant folders; the other generated files remain in your project.

Move each component definition to its own file, then import both into `main.py`:

```python
import sys

from velto import VeltoContext
from velto.ui import psx

from components.welcome import Welcome
from components.counter import Counter


class MyFirstVeltoApp(VeltoContext):
    def render(self):
        return psx("""
            <Flex direction="column" gap="12px">
                <Welcome name="Alex" />
                <Welcome name="Sam" />
                <Welcome name="Taylor" />
                <Counter />
            </Flex>
        """)


if __name__ == "__main__":
    sys.exit(MyFirstVeltoApp().run())
```

The `Counter` component keeps the same `use_state` and `on_click` code from [Your first interaction](/getting-started/first-interaction); only its location has changed.

Run your project as usual:

```bash
velto start
```

You should see the same greetings and interactive counter. Organizing code into files doesn't change what the user sees.

## What you've learned

You now know where the main parts of a generated Velto project belong:

- **`main.py`** starts the application.
- **`components/`** is a place for reusable interface pieces.
- **`views/`** is a place for larger screens or sections.
- **`resources/`** holds icons and other assets.
- **`settings/`** holds application and platform configuration.
- **`pyproject.toml`** and **`poetry.lock`** support Python dependency management.

You don't need to use every folder immediately. Start small, and separate your code when doing so makes the project easier to understand.
