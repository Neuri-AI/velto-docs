title: "Secrets and protection"
description: "Distinguish application secrets, encrypted frozen payloads, and publisher signing credentials."
---

Velto has **two different kinds of sensitive data** that must not be conflated: values the application needs at runtime, and credentials the publisher needs to sign a release. They have different lifetimes, consumers and packaging rules.

| | Runtime secrets | Signing credentials |
| --- | --- | --- |
| File | `settings/secrets.json` | `settings/sign.json` |
| Consumer | Application runtime | `velto sign` on the build/signing machine |
| Frozen distribution | Encrypted payload in `resources.pak` | Excluded from application packages |
| Examples | Client license value, scoped API token | PFX password, Apple notarization credentials |

## What happens to runtime secrets

In source mode, the Engine reads local `secrets.json` and merges its values into application settings. During a frozen desktop build, the CLI excludes the plaintext source file, encrypts the JSON object with **AES-256-GCM**, and places the payload inside the resource package. The Engine authenticates and decrypts the payload in memory before merging it into application settings.

The documented cryptographic pipeline uses **HKDF-SHA256**, a random salt and a random 12-byte nonce. The encrypted format carries a versioned `QYRSEC` header. That header is an internal format marker inherited from the Engine—not the name of the CLI command or the output directory.

Application code reads settings through the same runtime-facing settings interface in source and frozen modes. See [Runtime settings](/runtime/settings-and-configuration).

## Merge behavior matters

Secrets override corresponding application values. The runtime's merge is **shallow**: if a secret replaces a nested dictionary, do not expect missing sibling keys to be recursively preserved. Prefer flat secret keys or complete nested values.

## What must never enter the client

`settings/sign.json` contains publisher-only information and is intentionally excluded from both ordinary frozen data and protected packages. The build also rejects signing credentials incorrectly placed in runtime secrets. Use the dedicated signing configuration described in [Bundle and sign](/cli/bundle-and-sign).

Keep both files out of version control. Generate them locally or inject them through CI secrets. Never paste real keys into the public Settings Builder, and never log the merged settings dictionary.

## Limits of client-side secrecy

Encryption protects embedded data at rest and complicates casual extraction. A determined attacker controlling the client can inspect its memory or reverse engineer execution. For high-value server operations, keep authoritative secrets server-side and issue short-lived, scoped client credentials.

For broader encrypted packaging of assets and settings, see [Protected resources](/cli/protected-resources).

## Where secret settings belong

`settings/secrets.json` is a top-level JSON object whose keys override runtime values from `base.json` or the host platform file. Qyro Engine performs **shallow** updates: overriding a nested object replaces the whole object, not just one nested field.

The build rejects a `sign` object or legacy flat signing settings inside runtime secrets. `settings/sign.json` is an entirely different, local-only input to `velto sign`. See [Configuration files](/cli/configuration-files) for its complete field reference.
